# Bring-up checklist: Raven on a real Pi Zero 2 W

**Status: nothing here has run on hardware.** QEMU accepts things a real board
won't, so this lists every assumption Raven makes about the board, what backs it,
and how sure it is. Read it before the first boot, and update it after.

Statuses:

- **Verified**: I read a primary source (named) and it agrees.
- **Partly**: a primary source agrees on part of it; the rest is said.
- **Unverified**: an assumption. If it is wrong, the board will not behave.

Sources were read on 2026-10-30. "Manual" is the *BCM2835 ARM Peripherals*
datasheet; the Zero 2 W's chip (BCM2710A1) is in the BCM2837 family and uses the
same peripheral blocks at a different base address (item 5).

## What to look at first on the board

The activity LED shows how far Raven got, with or without a serial adapter
(decision 108):

| LED | Meaning |
|---|---|
| nothing, ever | The firmware never started Raven (SD card, `config.txt`, `kernel8.img` name), or Raven stopped before its first line of Rook |
| one flash | Raven's Rook code is running |
| then two flashes | The console (UART) has been set up. If the serial terminal shows nothing, suspect items 7 and 8 (wiring, baud rate, clock) |
| solid on | Boot complete: `Raven: boot complete, idling` was printed |
| flashes, then dark or part-way | Stopped after the last signal it gave |

A panic or fault does **not** change the LED yet: the emergency console is
assembly (decision 98), and a blink loop there would need its own test. Until
then a fault is only visible on the serial port.

## Checklist

| # | What Raven assumes | Evidence | Status |
|---|---|---|---|
| 1 | The firmware loads `kernel8.img` in 64-bit mode when `config.txt` has `arm_64bit=1` and `kernel=kernel8.img`, and jumps to its first byte at physical address 0x80000 (`kernel/link.ld`) | Official [config.txt page](https://www.raspberrypi.com/documentation/computers/config_txt.html) on `kernel`/`arm_64bit` (read as a search excerpt, not in full). 0x80000 is what other bare-metal projects use; I did not find it in an official document | **Partly** |
| 2 | `dtoverlay=disable-bt` gives the PL011 ("UART0") to GPIO 14 and 15 | Firmware [overlays README](https://github.com/raspberrypi/firmware/blob/master/boot/overlays/README): "Disable onboard Bluetooth ... restores UART0/ttyAMA0 over GPIOs 14 & 15" | **Verified** |
| 3 | `enable_uart=1` is harmless | The config.txt page says it requests a serial console and implies `core_freq=250` (that matters for the *mini* UART, which Raven doesn't use). Whether Raven needs it at all is not known | **Partly** |
| 4 | GPIO 14 and 15 on ALT0 are TXD0 and RXD0; their function fields are bits 12-14 and 15-17 of GPFSEL1; ALT0 is `100` | Manual, GPIO chapter: alternate function table, GPFSEL1 field table, function encodings | **Verified** |
| 5 | The peripherals sit at physical 0x3F000000 (GPIO 0x3F200000, UART0 0x3F201000) | Raspberry Pi [`bcm2837.dtsi`](https://github.com/raspberrypi/linux/blob/rpi-6.6.y/arch/arm/boot/dts/broadcom/bcm2837.dtsi): `ranges = <0x7e000000 0x3f000000 0x1000000>` maps the manual's bus addresses (0x7E...) to ARM addresses. The Zero 2 W's tree says `compatible = ... "brcm,bcm2837"` ([`bcm2710-rpi-zero-2-w.dts`](https://github.com/raspberrypi/linux/blob/rpi-6.6.y/arch/arm/boot/dts/broadcom/bcm2710-rpi-zero-2-w.dts)) | **Verified** |
| 6 | Pull-up/down is switched off for 14 and 15 with the sequence: write GPPUD, wait 150 cycles, write GPPUDCLK0, wait 150 cycles, clear GPPUDCLK0 (`raven/pl011.rook`) | Manual, GPPUDCLK registers: the six-step sequence. Raven does steps 1-4 and 6; step 5 (remove the control signal) is the same write as step 1 since the control is 0. `settle(150)` loops 150 times, and a loop iteration takes at least a cycle, so the wait is at least 150 cycles | **Verified** (QEMU ignores pulls entirely) |
| 7 | UART divisors for 115200 baud: IBRD 26, FBRD 3, which is right for a **48 MHz** UART clock | The formula `BAUDDIV = FUARTCLK / (16 x baud)` is in the manual (UART_FBRD). 48e6 / 1843200 = 26.04, and 0.04 x 64 = 2.7, which rounds to 3. **The 48 MHz clock is not verified** (item 8) | **Partly** |
| 8 | The UART clock really is 48 MHz, because `tools/sdcard/config.txt` sets `init_uart_clock=48000000` | I found no official statement of `init_uart_clock` or its default. A third-party mirror of old documentation says 48 MHz; a 2013 forum thread says the default was 3 MHz. At 3 MHz the divisors would be IBRD 1, FBRD 40. The kernel device trees don't say: the clock comes from the firmware at run time | **Unverified. The biggest risk for the serial port.** A wrong clock means a wrong baud rate and garbage or silence, with the LED still flashing |
| 9 | The transmit-FIFO-full flag is bit 5 of the flag register (`FR_TXFF = 0x20`) and `Pl011.put` waits on it | Manual, UART_FR: bit 5 "TXFF, Transmit FIFO full" | **Verified** the bit. The wait itself is **untested**: QEMU's UART sends instantly and never sets it |
| 10 | The activity LED is GPIO 29, active low (driven low it lights) | Mainline Linux [`bcm2837-rpi-zero-2-w.dts`](https://github.com/torvalds/linux/blob/master/arch/arm/boot/dts/broadcom/bcm2837-rpi-zero-2-w.dts): `&led_act { gpios = <&gpio 29 GPIO_ACTIVE_LOW>; }`. The Raspberry Pi tree's line-name list for the same board has `STATUS_LED_N` as the 30th entry (index 29), and its legend says a `_N` suffix means active low | **Verified** (two sources) |
| 11 | Pin 29's function field is bits 27-29 of GPFSEL2, and `001` makes it an output; GPSET0 is 0x1C, GPCLR0 is 0x28, GPLEV0 is 0x34 | Manual, GPIO chapter: register table and FSEL29 | **Verified**. QEMU's GPIO model does keep the pin level, so `rook/led_pin` checks the writes land |
| 12 | The ARM generic timer ticks at `CNTFRQ_EL0`, which the firmware sets, and EL1 may read it (`start.s` sets `CNTHCTL_EL2`) | The EL1 access is architectural. That the firmware sets `CNTFRQ_EL0` on this board is **not checked here**: other bare-metal Pi 3 projects rely on it. If it reads 0, `wait_ms` falls back to 19.2 MHz, which is also unchecked | **Unverified**. If wrong, the LED flashes at the wrong speed, or `wait_ms` never returns (if the counter doesn't run) |
| 13 | The firmware enters at EL2 or EL3 and `start.s` brings Raven to EL1; cores 1-3 are held by the firmware and also parked by Raven | QEMU enters at EL2 and `boot/hello` prints it. What the real firmware does for a `kernel8.img` on this board is not checked | **Unverified** |
| 14 | With the MMU and caches off, every access Raven makes is aligned | With the MMU off, memory is treated as device memory, where unaligned accesses fault. `Mmio` already insists on 4-byte alignment; Rook values live in 8-byte slots; text is read a byte at a time. I did not check Fledgling's generated code for anything else, and I don't know if QEMU enforces this | **Unverified** |
| 15 | The board has 512 MB of RAM | Tests run on `raspi3ap` (512 MB) as well as `raspi3b`. The Zero 2 W's memory size is from its product page, which I did not re-read | **Partly** |
| 16 | The serial adapter is 3.3 V, with its RX on pin 8 (GPIO 14, TX), TX on pin 10 (GPIO 15, RX) and GND on pin 6 | `tools/sdcard/README.md` (written from the Pi header pinout; not checked against a schematic) | **Partly** |

| 17 | Receiving works by polling: `FR_RXFE` (bit 4 of the flag register) is clear when a byte waits, and reading the data register takes it; polling once per scheduler turn is faster than 115200 baud fills the 16-byte FIFO (`raven/pl011.rook`, `UartReader`) | Manual, UART_FR "RXFE, Receive FIFO empty", UART_DR. QEMU's PL011 model accepts typed bytes and the echo demo passes on both machines | **Verified** the bit. **Untested on a board**: receive overruns, framing errors (the error bits in the data register are ignored), and whether the polling loop keeps up when other actors are busy. The send-cost numbers in docs/design.md 6.2 come from QEMU's timer and are not real times |

| 18 | The handler time budget works through the ARM local interrupt controller: bit 1 of `CORE0_TIMER_IRQCNTL` (0x40000040) sends the EL1 physical timer (`CNTP_*`) to core 0 as an IRQ, which Raven takes at EL1 (`kernel/arch/aarch64/actors.s`, `vectors.s`) | The BCM2836 ARM-local peripherals document (the same block the Pi 3 and the Zero 2 W's BCM2710A1 use, per mainline Linux's `bcm2836-l1-intc`); QEMU's `bcm2836_control` model, on which both test machines pass | **Partly**. The register and bit are from the documents and QEMU agrees; **untested on a board**: that the firmware leaves the timer unmasked for EL1, and that 100 ms is 1.92 million ticks of whatever `CNTFRQ_EL0` really is (item 12). If the interrupt never arrives, a runaway handler hangs the core as it did before; if it arrives early, ordinary handlers are reported as failed |

| 19 | UART interrupts: the UART is peripheral interrupt 57, which shows as bit 25 of `IRQ pending 2` (0x3F00B208); `IRQ enable 2` (0x3F00B214) and `IRQ disable 2` (0x3F00B220) switch it; the PL011's `IMSC` bits 4 (receive) and 6 (receive timeout) and `IFLS` = 0 (interrupt at 2 bytes) ask for it. Peripheral interrupts reach core 0 as an IRQ by default | BCM2835 ARM Peripherals, chapter 7 (interrupts, the register map and the IRQ numbering) and the PL011 manual; QEMU's `bcm2835_ic` and PL011 models, on which the echo test passes on both machines | **Partly**. The addresses and bits are from the manuals and QEMU agrees. **Untested on a board**: that the firmware leaves the default routing; the receive timeout (QEMU's PL011 may not model it, so a real board with 1 byte waiting is untested); that `IFLS` = 1/8 gives an interrupt at 2 bytes; overrun at 115200 baud if the `fired` handler is delayed; and `wfi` waking on the interrupt |
| 20 | The MMU and caches (milestone 6a, decision 171): the firmware hands over with the MMU and caches off, the image is loaded at 0x80000, RAM is 512 MB at 0, the peripherals are at 0x3F000000 (Device-nGnRE) and the ARM local peripherals at 0x40000000, page tables written with the data cache off are seen by the walker, and Normal memory takes unaligned accesses | Only QEMU, which implements none of the cache or memory-ordering behaviour. If the board hangs right after `Raven: running at EL1`, suspect this item first: try leaving the caches (C, I) off by changing `SCTLR_VALUE` in `kernel/arch/aarch64/mmu.s`. The RAM size and peripheral base are items 15 and 3 | Unverified |
| 21 | Protection domains (milestone 6b-2a, decision 174): EL0 code runs with its own TTBR0 and ASID, the kernel's and every domain's entries are non-global, so a switch needs no TLB invalidation; `isb` after writing TTBR0 is enough; an exception from EL0 finds SP_EL1 on a page every domain's table maps for EL1; the vectors run under the domain's table until they switch; code pages are executable at EL1 and EL0 together (read-only) | Only QEMU. It models ASIDs and the TLB but not their timing, speculation, or the cache effects of changing tables. If a board hangs or misbehaves on the first domain run, suspect this item: add `tlbi vmalle1` and `ic iallu` around the TTBR0 writes in `domain.s`, then look at PXN on the code pages (an EL0-readable page that EL1 executes is allowed, but some implementations are strict about it) | Unverified |
| 22 | Cores 1-3 (milestone 6d-1, decision 178): the firmware stub holds them in a spin table at 0xd8 + 8 * core (0xe0, 0xe8, 0xf0 for cores 1-3) until an address is written there and `sev` is executed; they arrive at EL2 with the MMU and caches off; their caches take part in coherency (`CPUECTLR_EL1.SMPEN`, which the firmware stub sets on every core, was not set by Raven); the table is cleaned to memory with `dc civac` before `sev` | Only QEMU's raspi3b/raspi3ap, which behave this way and did so every time in the test runs. The Pi firmware's armstub8 source describes the same table, from memory; not checked here | Unverified |
| 23 | Rings between cores (milestone 6d-2, decision 181): ordinary cacheable, inner-shareable memory is coherent between the four cores, `stlr`/`ldar` order a record's slot before its tail, `sev` sets the event register of every core and a `wfe` that finds it set returns at once (so no wakeup is lost), and `ldaxr`/`stlxr` on cacheable memory work between cores | Only QEMU, which runs the cores as threads and showed one race of its own (a message reaching an actor before its `new`, fixed); the counters, rings and exclusives have never run on cores whose caches are not coherent. If a board loses messages or hangs after the first cross-core send, suspect `CPUECTLR_EL1.SMPEN` (item 22) first | Unverified |
| 24 | Devices in a domain (milestone 7e, decision 182): a peripheral page mapped into a domain's table as Device-nGnRE, read/write at EL0, never executed, outer shareable, takes accesses from EL0 with the ordering Device memory promises; a table entry written by core 0 for a domain of another core is seen by that core's walker (`dsb ishst` after the write; no TLB invalidation, since a faulting translation is not cached); a 32-bit load or store to a PL011 register from EL0 behaves as from EL1 | Only QEMU, which does not model memory attributes, the walker's cache snooping or Device ordering. If a driver in a domain hangs or reads garbage on a board, suspect this item: try `tlbi vmalle1` and `dsb ish; isb` after the mapping, and check the walker's memory attributes in `TCR_EL1` (inner shareable, write-back) | Unverified |
| 25 | Waking a sleeping core (milestone 7f and 7l, decisions 183 and 191: every core idles in `wfi`): another core's write to a core's local mailbox 0 set register (0x40000080 + 16 * core) raises an IRQ on that core (enabled by bit 0 of 0x40000050 + 4 * core), the IRQ source register (0x40000060) shows it in bit 4, writing all ones to the write-clear register (0x400000C0) clears it; a pending IRQ wakes `wfi` even with IRQs masked; the virtual timer (`cntv_*`, routed by bit 3 of 0x40000040) expires 1 ms after being armed and wakes `wfi` too; an IRQ whose source has withdrawn is harmless | Only QEMU, which models the BCM2836 local mailboxes but left a core in `wfi` with the mailbox interrupt pending about one run in thirty (the timer covers it). The register layout is from memory of the BCM2836 ARM-local peripherals document and was not checked against it. If a board loses a message for core 0 until the next interrupt, suspect this item | Unverified |
| 26 | DMA (milestone 7h-7j, decisions 185 and 189): the address a device uses for a buffer in RAM is the ARM physical address plus the bus alias 0xC0000000 (the one that bypasses the caches), not the physical address itself; `dc civac` over the control block and both buffers before the transfer, and over the destination after it, makes the device see the CPU's writes and the CPU see the device's; the controller's channel registers are at 0x3F007000 + 0x100 * channel and its enable register at 0x3F007FF0; a transfer in progress when the driver's domain is wiped by a restart is stopped before the pool is reused (not built; a transfer cannot outlive the service's handler today, which waits for it, and a service refuses a driver that has ended, decision 199: both must change together when a transfer can be asynchronous) | The first two and the register layout are what the BCM2835 documentation says, and a copy through the alias works on QEMU's `bcm2835-dma` model (`trusted/dma_copy`), but QEMU also accepts the plain physical address (the mutation that left the alias out was caught by no test), so the alias is not shown to be needed. QEMU has no caches, so cache maintenance is unchecked, and the restart case is not built. If a transfer on a board copies stale data or nothing, suspect this item first | Unverified (a copy works on QEMU; nothing is checked on a board) |
| 27 | Giving a domain back (milestone 8c, decision 197): when a `separate` actor ends, core 0 clears the domain's device L3 table and L2 entries, executes `dsb ishst; tlbi aside1is, <ASID << 48>; dsb ish; isb` (the ASID is the domain number, the same on every core, so this also drops the entries of the same-numbered domain on other cores: wasteful, not wrong), and only then marks the domain free for a new tenant. The model (`recycle` in tools/modelcheck.py) says why: a translation of the old tenant's device page left in a core's TLB would let the new tenant, who was never given it, reach the device | Only QEMU, which flushes its whole TLB on every write of TTBR0 and so cannot show a stale entry: the tests (`separate_recycle_devices`) show the tables are cleared, not that the invalidation works. If a board lets a new tenant read a register it was not given, suspect this item: check that the `tlbi` is inner-shareable (`is`) and that the `dsb ish` is before the tenant starts; `tlbi vmalle1is` is the larger form | Unverified |
| 28 | Several actors in a domain (milestone 9b, decision 202): when an actor is placed in a live domain, one more page of its pool is made EL1-only (the L3 entry is rewritten with the EL1-only attributes, then `dsb ishst; tlbi aside1is, <ASID << 48>; dsb ish; isb`) before Raven clears it and uses it for the actor's header and mailbox; the domain may be running on another core at the time, with the page in its TLB as ordinary data. Giving the domain back writes all 511 entries again the same way | Only QEMU, which flushes its TLB on every write of TTBR0 and cannot show a stale entry: the tests show the page is not reachable after the remap (`trusted/domain_places`), not that the invalidation works on a core that kept the old translation. If a domain reads another actor's header on a board, suspect this item first: check that the `tlbi` is inner-shareable and complete before the page is cleared | Unverified |
| 29 | Memory a domain's EL0 code and Raven write on different cores (milestones 9c to 9d, decisions 203, 204, 206, 207): the runtime of a domain keeps its mailboxes, run queue and counters in the top of its pool; core 0 writes into a running domain's pool when it places an actor (`runtime_register`) or revokes one (`RT_S_GEN`), while the domain's own core reads and writes the same words at EL0; the two numbers Raven clamps (how far the ring was read, how many messages finished) are read by the domain's own core, between its turns, and since decision 211 so is everything a give-back touches (the ring's numbers, the hold, the wipe), core 0 only clearing the table and changing the handle's generation first. The domain's state word (free, open, closing, being given back) is written with a release and read with an acquire, so a core that sees a domain free sees its wipe done. There are no atomics and no barriers for these words: each word is written by one side at a time by construction (Raven writes while the domain is not running on that core, or before it can see the actor), and a number of the domain's that Raven reads is clamped or bounded (decision 208), so a stale one only delays work. One word per domain slot is the exception, and is atomic: the counter of generations (decision 209), in the core's block, which core 0 and the domain's own core both bump with load-exclusive/store-exclusive, as the count of unfinished messages is | Only QEMU, whose threads see each other's writes at once. The model checker (`python3 tools/modelcheck.py`, scenarios `inbound` and `restart_ring`) treats a read as seeing the latest write, which a core with a store buffer may not. What is certain to need the same assumption as items 22 and 23 is that the pools are Normal, cacheable and Inner Shareable on every core; if they are not, a mailbox word written by core 1 is not what core 0 reads. If a domain hangs or loses a message on a board and not on QEMU, suspect this item with 22 and 23; a stale `RT_S_GEN` after `revoke` means a reference revoked on core 0 can still be accepted by the fast path of another core for a short while (not forever: the next entry into the domain sees the word) | Unverified |
| 30 | The budget timer's interrupt is recognised by ENABLE and ISTATUS of `cntp_ctl_el0` together (decision 217, `irq_entry` in vectors.s and `domain_irq` in domain.s): `timer_disarm` writes 0 after every handler, and while ENABLE is 0 the architecture leaves ISTATUS UNKNOWN. Testing ISTATUS alone (the form until decision 217) worked on QEMU, which reads it as 0 when the timer is off | QEMU only, which cannot show an UNKNOWN value read as 1. If a board halted a core at the first UART or mailbox interrupt after a handler, with a report of a handler over its time budget, this was the cause; the form now does not depend on it | Unverified |
| 31 | A domain runs with FIQ masked and SError unmasked; an SError while it runs (an asynchronous abort, such as a device access of a driver the bus refused) fails the domain (`domain_serror`, decision 217) instead of halting the core in `exception_report` | Nothing on QEMU raises an SError or an FIQ for a domain, so neither path has run. If a driver's domain on a board makes its core stop with an 'SError, lower EL' report, the vector is not the one built here; an SError at EL1 still halts, by design | Unverified |
| 32 | `ring_push` has a `dsb st` between the store-release of a ring's tail and the write that raises the receiving core's mailbox interrupt (decision 217): a release does not order later stores, and the mailbox register is Device memory, so without it the interrupt could reach a core before the record, which would then sleep until its 1 ms backstop (decision 191) | QEMU orders these writes anyway and cannot show it. A board where a message between cores sometimes takes about 1 ms longer than usual would point here | Unverified |

## Reading the board's serial port with the test harness

`tests/run_tests.py` can read boot output from a serial port instead of QEMU's
(decision 110):

| `CORVOS_SERIAL` | Output comes from |
|---|---|
| unset | QEMU's own output (what `make test` uses) |
| `pty` | QEMU's serial port on a pseudo-terminal, read the way a real port is. Slower to start, and used to test the harness |
| `/dev/ttyUSB0` (or similar) | A real board. Only `boot/hello` runs: the kernel is whatever is on the SD card |

On a board, start (or reset) it after the harness says it is reading:

```
CORVOS_SERIAL=/dev/ttyUSB0 python3 tests/run_tests.py boot/hello
```

**Not built yet:** flashing a given image, and resetting the board by itself. That
is the "real hardware in CI" step in [roadmap.md](roadmap.md#later-real-hardware-in-ci),
which needs the board, a USB-serial adapter and a way to power-cycle it.

## If I could change one thing first

Item 8. Instead of assuming the UART clock, Raven should ask the firmware for it
(over the mailbox property interface; I believe the request is "get clock rate" for
the UART clock, but I have not checked that against its documentation) and work out
the divisors. That removes the largest guess on this list, but it needs a mailbox
driver, so it is a separate piece of work.
